# Mejoras de Cognia — 2026-08-28

Documentación de la tanda de trabajo sobre el **CLI de Cognia**: mejorador de
prompts consciente del contexto, encuestas interactivas, librería de memorias,
biblioteca de flujos con versionado, y medición real del contexto GPU/RAM.

Todo lo que hay aquí tiene puerta en el CLI y se probó tecleándolo.

inventario previo dio esto:

## 2. Decisiones técnicas y por qué

### 2.1 El catálogo es una VISTA, no un almacén

Cognia guarda artefactos en once sitios con tres formatos de índice (SQLite,
JSON por carpeta, JSONL append-only). La tentación era migrarlo todo a una
tabla nueva. No se hizo: sería una **cuarta** fuente de verdad que se
desincroniza con las otras tres. El propio repo ya documenta que el
`index.json` de programas no coincide con el disco (`autoprueba.py:125-129`).

`catalogo.py` lee cada familia con la función que ya existía y probada
(`storage.list_programs`, `generalizador.listar_flujos`, `skills.load_skills`,
`checkpoints.listar`, `papelera.lotes`) y las proyecta a una fila común. Una
vista no se puede desincronizar porque no guarda nada.

**Consecuencia honesta declarada:** el catálogo es tan bueno como sus fuentes.
Si un índice miente, el catálogo repite la mentira. Por eso cada fila lleva
`fuente` y cada familia que falla deja un aviso visible.

### 2.2 Restaurar una versión NO borra el historial

`restaurar(flujo, v2)` estando en la v3 crea la **v4** con el contenido de la
v2. La v3 sigue ahí.

No es purismo. La restauración la va a pedir muchas veces el **modelo**,
conversando ("vuelve a como estaba antes"), y un modelo que puede truncar el
historial puede destruir trabajo con una frase ambigua. Con append-only, la
peor consecuencia de una restauración equivocada es otra restauración.

### 2.3 El modelo propone, `flows.validar()` dispone

En la edición conversacional y en `session-to-workflow`, el modelo devuelve un
DAG completo (no un parche) y se valida contra el **mismo** validador que usa
el ejecutor. Un ciclo, un wire colgado o una tool inexistente se rechazan y el
flujo anterior queda intacto.

Se pidió el flujo entero y no un parche a propósito: los parches obligan a
interpretar posiciones y el modelo se equivoca; el DAG entero se valida de una
pieza y, si está mal, no se aplica nada.

### 2.4 Las encuestas solo corren donde no molestan

Tres filtros en cascada:
1. Solo en el camino `preguntar` del mejorador — cuando el usuario **ya eligió**
   mejorar esa línea. En modo `auto` no hay encuestas: el trato de `auto` es
   que el usuario no toca nada.
2. Solo sobre pedidos de menos de 320 caracteres (uno largo ya trae sus
   decisiones tomadas).
3. El generador puede devolver cero preguntas, y eso es una respuesta
   **correcta**, no un fallo.

## 3. API interna

### `cognia.memory.catalogo`

```python
construir(familias=None, *, limite_por_familia=0) -> Catalogo
buscar(cat, consulta, *, tope=8, familias=None, minimo=1) -> list[Fila]
familias_disponibles() -> tuple
```

`Fila`: `id, familia, titulo, resumen, ruta, creado, modificado, bytes,
etiquetas, estado, relaciones, fuente`.

`Catalogo`: `filas, avisos, ms, familias_ok, familias_fallidas`.

**Punto de extensión:** añadir una familia es escribir su lector y registrarlo
en `_LECTORES`. Ningún consumidor cambia.

### `cognia.harness.contexto_mejora`

```python
reunir(texto, *, historial=None, cwd="", presupuesto_chars=1800,
       secciones=None, proveedores=None, presupuesto_ms=1200,
       permitir_caros=False) -> Contexto
tipo_de_tarea(texto) -> str
faltantes_por_tipo(texto, tipo="", *, contexto="") -> list
```

`Contexto`: `bloque, secciones, faltantes, tipo_tarea, avisos, ms, chars,
recortadas`.

Secciones por orden de prioridad (y de recorte inverso): `entorno`,
`conversacion`, `restricciones`, `artefactos`, `recetas`, `skills`,
`memorias`, `rag`.

**Punto de extensión:** `_PROVEEDORES` es un dict `{nombre: fn(texto, estado)}`.

### `cognia.harness.encuesta`

```python
vale_la_pena(texto, *, faltantes=None) -> (bool, motivo)
preparar(texto, *, contexto="", faltantes=None, max_preguntas=3,
         generar_fn=None) -> Encuesta
incorporar(texto, respuestas) -> str
```

`Pregunta`: `id, tipo ('abierta'|'unica'|'multiple'), texto, opciones, porque`.

### `cognia.agent.flujoteca`

```python
guardar(flujo, *, nombre="", nota="", descripcion="", validar=True) -> meta
listar() -> list        cargar(nombre, version=None) -> flujo
versiones(nombre) -> list
restaurar(nombre, version, *, nota="") -> meta
comparar(nombre, v1, v2) -> dict
borrar_version(nombre, v, *, quien="ia", politica="nunca") -> {ok, motivo}
borrar / renombrar / duplicar / describir / existe
```

### `cognia.agent.flujo_ia`

```python
editar(flujo, instruccion, *, generar_fn=None, tool_existe=None,
       listar_tools=None) -> Resultado
de_sesion(historial, *, nombre="", pasos_reales=None, ...) -> Resultado
sanear_flujo(crudo, *, tool_existe=None, nombre_previo="") -> (flujo, motivo)
```

Con `ok=False`, `Resultado.flujo` es **exactamente** el que entró.

### `cognia.harness.medidor_contexto`

```python
medir(url="", *, timings=None) -> Instantanea
formato_humano(inst) -> str      formato_tecnico(inst) -> str
```

Cada campo es una `Medida(valor, unidad, origen, fuente, nota)` donde `origen`
es `"medido"`, `"estimado"` o `"?"`. **Un número sin origen no sale de este
módulo.**

### `cognia.ux.selector` (ampliado)

```python
elegir_varias(titulo, opciones, marcadas=None, input_fn=None,
              permitir_vacio=True) -> list | None
texto_libre(pregunta, default="", pista="", input_fn=None,
            multilinea=False) -> str | None
```

En las dos, `None` significa **canceló** y `""` / `[]` significan **contestó
que nada**. Quien las consume decide distinto en cada caso.

## 5. El sistema de contexto GPU + RAM

### 5.1 Qué permite REALMENTE llama.cpp

Esta es la parte donde la idea de partida tuvo que corregirse. El pedido era
"KV caliente en VRAM, KV frío en RAM, con recuperación bajo demanda".

**llama.cpp NO hace paginación de KV por token dentro de un contexto activo.**
No existe ese mecanismo. Lo que sí existe, verificado sobre el binario real
(build 10434, `llama-server --help`):

| Flag | Qué hace de verdad |
|---|---|
| `--cache-ram N` (MiB) | Prompt cache en RAM del sistema. Cuando un slot queda **inactivo**, su KV se serializa a RAM; si vuelve un prompt con el mismo prefijo, se restaura a VRAM |
| `--cache-idle-slots` | Activa lo anterior (por defecto sí, requiere `--cache-ram`) |
| `--no-kv-offload` | KV **entero** en RAM. Todo o nada — justamente lo que el pedido descartaba |
| `--cache-type-k/v` | Cuantización del KV (`q8_0` ocupa la mitad que `f16`) |
| `--ctx-checkpoints N` | Puntos de control por slot |
| `--kv-unified` | Un solo buffer KV compartido entre secuencias |

Es decir: **el reparto caliente/frío existe, pero a granularidad de
CONVERSACIÓN, no de token.** Una conversación inactiva no ocupa placa; la
activa vive entera en VRAM. Eso es exactamente "usar RAM como extensión del
espacio de contexto sin sacrificar la GPU", solo que la unidad no es la que se
suponía.

### 5.2 Qué se cambió

**`node/llama_backend.py`:**

1. `--cache-ram` pasó de un **1024 fijo** a un cálculo sobre la RAM libre real
   (25%, acotado a `[1024, 8192]` MiB). El 1024 venía de cuando coexistían 3-4
   servidores en 12 GB; con un solo cerebro y 31 GB de RAM dejaba el 96% de la
   RAM sin usar para lo único que la puede aprovechar. `LLAMA_CACHE_RAM_MIB`
   sigue mandando.

2. Se añadió `--metrics`. Sin él, `/metrics` devuelve HTTP 501 y Cognia no
   puede reportar el uso real del KV.

### 5.3 El banco: qué cuesta cada configuración

Qwen3.8-27B-Ridge, RTX 5060 Ti 16.311 MiB, 31,9 GB RAM, llama.cpp build 10434.
Prompt del 50% de la ventana con una aguja plantada por el medio, 200 tokens
generados, la máquina **limpia** (375 MiB de VRAM de línea base).

| KV cache | ctx | VRAM MiB | RAM proc | prefill tok/s | gen tok/s | aguja |
|---|---:|---:|---:|---:|---:|:--:|
| q8_0 en VRAM | 8.192 | 11.752 | 11.562 | 786,5 | **30,04** | sí |
| q8_0 en VRAM | 32.768 | 12.678 | 11.589 | 780,7 | **28,42** | sí |
| q8_0 en VRAM | 65.536 | 13.926 | 11.626 | 744,0 | **26,37** | sí |
| f16 en VRAM | 8.192 | 11.992 | 11.559 | 795,1 | **30,27** | sí |
| f16 en VRAM | 32.768 | 13.552 | 11.588 | 783,9 | **29,15** | sí |
| f16 en VRAM | 65.536 | **15.632** | 11.625 | 747,5 | **27,57** | sí |
| q8_0 en RAM | 8.192 | 11.356 | 11.995 | 655,1 | **12,05** | sí |
| q8_0 en RAM | 32.768 | 11.520 | 12.839 | 641,4 | **9,18** | sí |
| f16 en RAM | 8.192 | 11.342 | 12.232 | 648,3 | **11,30** | sí |
| f16 en RAM | 32.768 | 11.438 | 13.798 | 636,5 | **7,52** | sí |

**Cuantizar el KV (q8_0) casi no cuesta velocidad, y compra margen:**

| ctx | q8_0 ahorra | y cuesta |
|---:|---:|---:|
| 8.192 | 240 MiB | 0,8% |
| 32.768 | 874 MiB | 2,5% |
| 65.536 | **1.706 MiB** | 4,3% |

**Mandar el KV entero a RAM (`--no-kv-offload`) es carísimo:**

| ctx | f16 → RAM | q8_0 → RAM |
|---:|---:|---:|
| 8.192 | **−62,7%** de velocidad | −59,9% |
| 32.768 | **−74,2%** de velocidad | −67,7% |

#### Qué significa esto

1. **`--no-kv-offload` no es la respuesta.** Cuesta entre el 60% y el 74% de
   la velocidad de generación para ahorrar 0,6–2,1 GB. La intuición del pedido
   ("no mandes todo el KV a RAM") era correcta y ahora está medida.

2. **q8_0 es el default correcto, pero no por velocidad.** Es 2-4% *más lento*
   que f16 en igualdad de condiciones. Lo que compra es **margen**: a 65K, f16
   deja 679 MiB libres de placa y q8_0 deja 2.385. Con 679 MiB, abrir el
   navegador te tira por el precipicio.

3. **El precipicio es real y lo medí sin querer.** La primera corrida de este
   banco se hizo con 4.220 MiB de escritorio encima, y f16 a 32K dio **66
   tok/s de prefill** contra los 783,9 de la corrida limpia. Un factor 12 de
   diferencia por tener el navegador abierto. Ese es el modo de fallo que la
   cuantización del KV evita.

4. **El techo práctico son 65.536 tokens.** A 131.072 el servidor arranca,
   `/props` confirma el contexto y la petición **se cuelga**: 600 s de timeout
   tanto en f16 como en q8_0. No es un OOM: es que lo que no cabe lo sirve la
   RAM del sistema y el prefill se arrastra. Coincide con el barrido que ya
   documentaba `cognia/agent/perfiles_arranque.py`.

5. **La calidad no se degrada.** La aguja plantada por el medio del prompt se
   recuperó en las 10 configuraciones, incluidas las de 65K.

**El mejor compromiso contexto ↔ velocidad en esta máquina: q8_0 en VRAM a
65.536 tokens** (26,4 tok/s, 13,9 GB de VRAM, 2,4 GB de margen). Es exactamente
lo que `perfiles_arranque.py` ya tenía configurado; el banco lo confirma de
forma independiente y ahora además dice *por qué*.

### 5.4 Qué se puede medir y qué no

`/contexto-vivo avanzado` lo dice campo por campo:

| Dato | Fuente | Origen |
|---|---|---|
| Contexto servido y **en uso** | `GET /slots` | medido |
| tok/s prefill y generación | `timings` de la respuesta | medido |
| Uso del KV (fracción) | `GET /metrics` (necesita `--metrics`) | medido |
| VRAM usada/total | `nvidia-smi` | medido |
| RAM libre/total | API del SO | medido |
| Tipo de cuantización del KV | línea de comandos del servidor | medido |
| Dónde vive el KV (política) | línea de comandos del servidor | medido |
| TTFT | `prompt_ms + 1/velocidad` | **estimado** |
| Bytes/token del KV | geometría del modelo | **estimado** |

**No se puede saber:** cuántos MiB de KV hay en VRAM contra en RAM. llama.cpp
no lo publica. Se informa la **política** (que es verdad) en vez de un reparto
en MiB (que sería inventado).

## 6. Limitaciones conocidas

1. **Paginación de KV por token: no existe.** Ver 5.1. Cualquier política
   hot/cold más fina que "conversación activa vs inactiva" requeriría parchear
   llama.cpp.

2. **`/metrics` solo si el servidor arrancó con `--metrics`.** Cognia ya lo
   pasa desde esta tanda, pero un servidor arrancado a mano antes no lo tiene,
   y `/contexto-vivo` lo dirá en vez de callarlo.

3. **El dashboard de Memorias no puede escribir en disco.** Un HTML estático
   servido por `file://` no puede borrar un fichero. El reparto es explícito y
   se dice en la propia página: la página sirve para **entender** qué hay, y el
   CLI para **cambiarlo**. Cada ficha trae el comando exacto con botón de
   copiar. Un test (`test_todas_las_acciones_existen_en_el_cli`) verifica
   contra el dispatch real de `cli.py` que ningún comando sugerido es
   inventado — la primera versión de esa tabla tenía cuatro que no existían.

4. **Generar una encuesta cuesta ~10-15 s** con el 27B a 20-30 tok/s. La caída
   es blanda (semilla determinista), pero el coste está ahí. La vía de mejora
   es servir la encuesta con un modelo pequeño de la flota en vez del cerebro.

5. **El primer uso del RAG en un proceso cuesta 7,4 s** (montar el índice del
   mapa de contexto). Se resuelve saltándolo en la primera llamada y
   calentándolo en un hilo de fondo; de la segunda en adelante son 15 ms. La
   primera mejora de cada sesión va sin la sección `rag`.

6. **`detectar_backend()` se deja engañar por `tailscaled`**, que escucha en
   `:8080` sobre la IP de tailscale. `medidor_contexto` lo esquiva prefiriendo
   el bind de `127.0.0.1`, pero el detector general del repo sigue con el
   problema (síntoma: 20 s de espera antes de un timeout).

7. **`~/.cognia/config.env` tiene `LLAMA_CTX_SIZE=200192`**, calibrado para el
   Qwythos-9B anterior. Hoy la receta por modelo lo pisa con un aviso, pero la
   perilla rancia sigue ahí y es una trampa para cualquier ruta que no lea la
   receta.

8. **Bug de datos preexistente:** `semantic_memory.description` de los
   conceptos `agente_tarea_completada` y `respuesta_streaming` contiene un
   **vector de embeddings**, no texto. El catálogo lo detecta, muestra una
   marca honesta y **avisa**; no lo arregla, porque arreglarlo es tocar quien
   lo escribe, no quien lo lee.

### 7.1 Aviso sobre el banco

`banco_kv.py` marca cada celda con `linea_base_sucia` si la GPU ya tenía más
de 1500 MiB ocupados al empezar. **No es cosmético.** La primera corrida dejó
dos celdas medidas con 4220 MiB de escritorio encima contra una con 435 MiB, y
el resultado fue absurdo: f16 a 32K daba 66 tok/s de prefill y f16 a 65K daba
750. Un contexto mayor no puede ir once veces más rápido; lo que cambiaba era
el escritorio. Las celdas con la marca puesta **no son comparables** con las
medidas en frío.
